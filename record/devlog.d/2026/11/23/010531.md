**Going wrong, found by review.** LEAD-175's scripts were written
resumable, and the run-lead skill asks for that: computations persist per
item. But the persistence was two writes where it needed one, or a
completion key coarser than what was written. In `posterior.py` the
output and the sampler state were saved separately. In `sgd_sweep.py` one
written line marked a whole job done. Both are safe when a run either
finishes or never starts, and unsafe exactly in the case resumability
exists for. Nothing caught it, because no test interrupted a write. A code
review the owner forwarded found both.

**What fixed it, and the lesson.**
- Write the progress marker and the state as one atomic unit. Here that is
  a checkpoint replaced by rename after the output line is synced.
- Reconcile on start, and stop when reconciliation fails.
- Key completion on exactly what each line records.
- Test the interruption itself, in `test_resume.py`.

The run-lead skill's persistence step could say so. That is left as a
proposal: a change to the skill's step is a procedure change, and only one
lead has shown the need.

**Audit.** The committed SGD results are complete. The posterior outputs
are consistent, but cannot show that no stale resume happened, so that
part is stated as likely, not shown. The note on LEAD-175 says which.
