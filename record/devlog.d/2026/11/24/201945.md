**Going wrong.** The owner suspected, on 2026-11-24, that they had
"inadvertently killed" the back-merge when merging staging into main
(#743). They had not, directly: the Docs run on that push failed at
`docs-lint` on one violation (SYNTHESIS-124's history listed version 3
before version 2), and `back-merge` needs `docs-lint`, so it was skipped.
Staging went a day without main's concretized codes, and nothing said so:
a skipped job shows grey, not red, and the red that caused it sits on a
run nobody watches after a promotion.

**The wrong theory.** That the owner's manual merge bypassed the
workflow. The run history showed the workflow did start; the job graph
showed where it stopped.

**Fixed.** Staging fast-forwarded to main by hand (it was a strict
ancestor, so the script's merge would have been the same), and the
history reordered (dmarx/nucleation#788).

**For the retro.** Whether `back-merge` should depend on `docs-lint` at
all: main is already pushed when lint runs, so holding the back-merge
does not protect main, and it leaves staging stale. Running it on
`always()` after `docs-generate`, or having a red lint on main open an
issue, would make the failure loud. That is a CI change, so the owner's.
