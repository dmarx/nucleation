# LEAD-tmpn6mi2: Build a temporal dependency graph of the record from its git history: an event log of every entry's substantive revisions, standing changes and typed relation additions and removals, kept apart from mechanical edits, and a developmental profile for every claim

## Why

The reference graph says how the record is organized now; its history says
how that organization changed (A33). Every later pilot of A34's shortlist
reads this one's output: the phase space (LEAD-tmp14mq0), the activity
half of mark-and-review (LEAD-tmp79qro), the mediation ratio of compaction
(LEAD-tmpd85zk) and the historical replay (LEAD-tmpe579v). It also redoes
two measurements the record already made without git dates: CLAIM-184's
count of citations after retirement (note of 2026-11-06, first caveat) and
CASE-307's revision rates (CLAIM-tmp4fc0k's defeater).

## What to build

All under `scratch/studies/lead-<code>/`, scripts and tests committed, the
large derived tables regenerated by the scripts and not committed (as
LEAD-199 did). No change to luria, to `luria.yaml` or to any entry: the
statistics are a projection, not metadata copied into entries (A33 §12:
"The derived statistics should remain projections").

**1. The event log**, one row per event:

| column | meaning |
|---|---|
| `entry` | the entry's final code, resolved from a temporary code through `formerly:` |
| `scheme` | CLAIM, QUESTION, TERM, CASE, ARG, LEAD, THEORY, SYNTHESIS |
| `event` | one of the classes below |
| `field`, `target`, `old`, `new` | for a relation, the field and the code added or removed; for a status, the old and new value |
| `commit`, `author_date` | the development clock |
| `promoted_date` | the date of the Promote merge that first carried the commit to main: the canonical clock (A33 §13: "when a change was developed and when it acquired operative standing") |
| `pr`, `files_in_commit` | the pull request where the merge commit names one, and how many entries the commit touched |
| `mechanical` | true for the classes in the last row of the table |

Event classes, from A33 §1, with the rule that assigns each:

| class | rule |
|---|---|
| created | the commit adding the file |
| statement revised | `title` or `statement` changed after normalisation |
| body revised | body outside `## Note of …` sections changed after normalisation (LEAD-199's `classify.py`) |
| defeater revised | `defeated_if` changed |
| dated note | a `## Note of …` section added |
| status transition | `status` changed; old and new kept |
| relation added / removed | a code added to or dropped from a declared reference field; recorded on the entry whose field holds it, and as `incoming` on the target |
| integrated | a SYNTHESIS's `integrates` gains the entry |
| superseded | `superseded_by` set |
| mechanical | commits by the CI bot (link targets, converse fields); commits named as repair, regenerate, promote or concretize; a field going from absent to present across more than 20 entries in one commit (a backfill); a vocabulary or retitling sweep, listed by hand from the ADRs that ordered them (ADR-070's "endorsement" to "conferral", ADR-148's retitling) |

Converse fields that `luria link --fix` writes (`supports`, `argued_by`,
`integrated_by`, `objected_by`, `advanced_by` and the rest) are not events:
the underlying relation is counted once, on the entry that states it (A33
§13). Generated views under `docs/` are excluded altogether.

**2. A developmental profile for each claim**, at any date `t`, computed
from the log. A34's metrics, with the choices A leaves open fixed:

- *last substantive revision* (statement, body or defeater revised), and
  days since it: prose stability;
- *new dependents in 7 and 30 days*: incoming `rests_on`, `grounds`,
  `objects_to`, `corroborates`, ARG `concludes`, LEAD `advances` added in the
  window: recent influence;
- *time to first downstream use*: days from creation to the first incoming
  `rests_on` or `grounds` (A34's "nucleation latency");
- *reactivation*: a gap of at least 21 days with no non-mechanical event,
  followed by one;
- *maintenance-only edits*: mechanical events and dated notes that change
  nothing else, as a count: the cost of persistence;
- *interaction intensity* (A33 §3), `I_i(t) = Σ_e exp(-(t - t_e)/τ)` over
  the entry's non-mechanical events, computed separately for each event
  class and for τ = 7, 30 and 90 days. Separate intensities replace A's
  weights `w_e`, which A leaves free and which would otherwise be chosen
  after seeing the data;
- *neighbourhood activity* (A33 §6), `N_i(t) = Σ_j W_ij I_j(t)`, with `W` a
  0/1 matrix per neighbourhood: downstream (entries that rest on or are
  grounded in `i`), upstream (`i`'s own premises), dialectical (objections
  either way), synthesis (accounts integrating `i`), developmental (leads
  advancing `i`, questions it bears on or answers). Reported per
  neighbourhood, never summed;
- *event entropy* (A33 §9) over the classes, and *status volatility*, the
  number of status transitions.

## How to extract

- Walk the non-merge commits of `origin/staging` that touch `record/`, in
  author-date order, as LEAD-199's `extract.py` does, reading each touched
  entry's blob at the commit and at its parent and diffing field by field.
  Do not use `git log main --first-parent`, as A33 §12 suggests: on this
  record work reaches main only through the nightly Promote merge
  (ADR-116), so main's first-parent history is one commit per promotion,
  with every temporary code renamed in it. Main's history gives only
  `promoted_date`.
- Read frontmatter with luria's own reader (`luria.adr_index.read_document`),
  so the fields are those the record's contract reads.
- The clone must have full history (`git fetch --unshallow` if it is
  shallow; the session's checkout of 2026-11-26 was not).
- Reuse `classify.py` and its tests for the body; add tests for each new
  class, on synthetic diffs, before the first full run.

## What would count as success, and as failure

The pilot succeeds as infrastructure when all of these hold:

1. **It reproduces CASE-307.** Restricted to 2026-10-07 to 2026-11-22 and to
   inbound `rests_on` and `grounds`, the edge counts agree with LEAD-199's
   `edges.json` (810 added, 79 removed) within 2 %, and the matched-age
   Mantel-Haenszel ratio of substantive revision, any inbound against none,
   falls inside CASE-307's interval, 1.22 to 1.77.
2. **Its classes are right.** A hand-check of 50 events, 10 drawn from each
   of statement or body revised, relation added, status transition, dated
   note and mechanical, finds at least 45 correctly classed and no class
   below 8 of 10.
3. **Identities resolve.** Every claim file on staging has exactly one
   `created` event, and fewer than 1 % of events keep a temporary code.
4. **Profiles check by hand.** For 10 claims drawn at random, the date of
   last substantive revision and the inbound count at today's date agree
   with what `git log -p` and the file show.
5. **It reruns.** One command from a clean full clone rebuilds the log and
   the profiles.

It fails, and says something, if:

- check 1 fails: the extraction differs from LEAD-199's, and no new measure
  is trusted until the difference is found;
- check 2 fails on mechanical against substantive: the profiles are
  reported by commit counts only, with that caveat, and LEAD-tmp14mq0 does
  not go on to test CLAIM-tmpk015q;
- more than 5 % of relation changes on a sample of merged pull requests
  appear only in merge resolutions, which a walk of non-merge commits
  misses (CASE-307's dating caveat): the walk is extended to merge commits'
  first-parent diffs on staging.

## Left for later

A33's revision cascades and "unanswered change" (how many entries a
premise's revision could affect that receive no recorded reconsideration)
are left out of this pilot. A33's own table says why the second is fragile:
"Prose unchanged despite reconsideration: Do not infer absence of review
from absence of edits"; and CLAIM-664 holds that whether a dependant falls
is a judgement no rule over the graph can make. Survival curves go to
LEAD-tmpe579v; regime discovery by clustering or change points to
LEAD-tmp14mq0; semantic comparison by embeddings or a model, which A33 §4
reserves for cases textual measures cannot settle, to a later lead.

## Cost

LEAD-199's extraction and classifier took an afternoon for claims and two
relation fields. Widening them to every reference field, status, eight
schemes and two clocks, with the tests and the 50-event hand-check: one to
two days of a delegated worker. The hand-check is the part to do slowly.
