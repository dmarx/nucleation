**Going right.** The run-lead skill's rule of one commit and push per step
held up across a fifteen-work batch: each work's NOTE, THEORY, LIT version
and dated notes went in one commit, with PROGRESS.md updated in the same
push, so a stop at any point would have lost one work at most. Small
helper scripts kept in the scratchpad (one moving a LIT to its new version
from a JSON spec, one appending a dated note, one checking every double
quotation against the downloaded text, one listing cited codes not in
force and not excused) made the fourteen filings uniform and let every
quotation be checked by script rather than by eye. Reading in the order of
what the claims most needed put the works with concrete bearings
([QUESTION-063](../../record/questions.d/QUESTION-063.md), [CLAIM-153](../../record/claims.d/CLAIM-153.md), [QUESTION-252](../../record/questions.d/QUESTION-252.md)) first, which is where the one new
claim came from.

**Going wrong.** To discard a scaffolded NOTE the worker ran
`mv <file> /dev/null` as root. That replaced the device with a regular
file, which other workers on the same machine would then have written
into and read from. It was noticed on the next command and the device
recreated (`mknod -m 666 /dev/null c 1 3`) within a minute; nothing else
was seen to fail. The safe idiom is `rm` on the file, or `git clean` on a
path the worker created. A shared machine turns a private slip into
everyone's.

**Also.** The worktree guard refused several compound commands (heredocs
mixed with `git`, or text the guard could not parse). Writing inputs to
files with the editor and running one plain command per call always
passed; batching edits and commits into one shell line did not.
