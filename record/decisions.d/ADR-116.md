# ADR-116: Work merges into a staging branch through pull requests, and a Promote workflow merges staging into main nightly or on demand, concretizing a batch's temporary codes at once and merging main back; so units cite each other's codes without stacking, and the tooling fits how the work is done

## Context

[ADR-071](ADR-071.md) puts each unit of work on its own branch, cut from the default branch.
When units cite each other's temporary codes, each has to be based on the
last, and a session's work becomes a stack: six pull requests on 2026-11-20
and 21 (558 to 563), five on 2026-11-19 (535 to 540, folded top-down by hand,
[POSTMORTEM-001](../postmortems.d/POSTMORTEM-001.md)).

The owner named the cost: each merge into main means waiting on CI. Reading
docs.yml shows where the wait is. Pushes to main already coalesce, since their
concurrency group holds one pending run. What repeats per merge is
retargeting: when a stack's bottom pull request merges, the next is retargeted
to main and checked again, and main has meanwhile concretized the merged
pull request's temporary codes (`allocate: merge`, done only where merges
serialize), so the next has to absorb renames. [POSTMORTEM-003](../postmortems.d/POSTMORTEM-003.md) records the
conflicts that came from this.

The owner's stated philosophy is to fit the tooling to the way the work is done
rather than the other way round. The record holds that idea in its own terms:
[CLAIM-541](../claims.d/CLAIM-541.md) reads wu-wei as control placed and timed where a system's own
dynamics do most of the work. Here the work's own rhythm is a run of small
units in a session, reviewed and promoted as a batch.

## Decision

- **A long-lived branch, `staging`.** Work branches are cut from staging and
  their pull requests target it. docs-check runs on each, as now (its trigger
  has no branch filter), repairing and linting.
- **Temporary codes stay temporary on staging.** Concretization still happens
  only on main. A unit that cites another unit's codes is cut from staging once
  that unit has merged into staging; it does not stack on the other's branch.
- **Promotion, by a new workflow, Promote** (`.github/workflows/promote.yml`),
  nightly and on demand. If staging is ahead of main: merge staging into main;
  lint the merged tree; push; run the generate step with concretization, as
  docs-generate does on a push to main; lint the result; merge main back into
  staging. A push made with GITHUB_TOKEN starts no other workflow, so Promote
  runs those steps itself. It shares docs.yml's `docs-main` concurrency group,
  so it never runs beside a direct push to main. Pages also listens for it.
- **Promotion by hand** is a pull request from staging into main, or running
  the workflow, whenever the owner judges a batch ready.
- **Only the workflow or the owner merges into main.** CI on main is unchanged.
- [ADR-071](ADR-071.md) holds with "cut from staging" for "cut from the default branch"; it
  takes a history note. [ADR-054](ADR-054.md) holds as it stands.

## Alternatives considered

- **Disable CI on main while merging a stack.** The owner's first idea. It
  would leave main unchecked in the meantime and still concretize per merge.
- **Fold stacks by hand** ([POSTMORTEM-001](../postmortems.d/POSTMORTEM-001.md)): merge each pull request into the one
  below and the bottom into main. Works, but must be done each time and still
  needs stacking while the work is open.
- **GitHub's merge queue.** Batches merges into main, but needs repository
  settings this session cannot change, and concretization would still run per
  batch entry.
- **Automatic promotion without the lint gate.** Cheaper, but would let a red
  batch reach main.

## Consequences

- Stacks go away for units that only cite each other: each is cut from staging.
- Branches open across a promotion still see the renames, once per batch rather
  than once per merge. Whether repair rewrites citations of a concretized code
  through its `formerly` field is to be checked at the first promotion.
- A promotion with a conflict on the back-merge (staging moved during the run)
  fails its last job and is resolved by hand.
- Until this pull request reaches main, Promote does not exist there: the
  first promotion is by hand, a pull request from staging into main.
- CLAUDE.md's working section says to cut from staging and open pull requests
  into it.

## First application

The stack of 2026-11-20 and 21 was folded into staging on 2026-11-21: pull
requests 558 to 563, each retargeted to staging and merged in order. Staging
then stood 28 commits ahead of main. This pull request goes into staging too;
the first promotion, by hand, will carry all of it to main in one run.
