**What happened.** The owner merged the promotion pull request (610) into main at about 22:44. Its docs-generate made the batch's temporary codes permanent: [ADR-137](../../record/decisions.d/ADR-137.md) became [ADR-137](../../record/decisions.d/ADR-137.md) and [RETRO-008](../../record/retrospectives.d/RETRO-008.md) became [RETRO-008](../../record/retrospectives.d/RETRO-008.md). While that was running, the assistant merged pull request 614 into staging. 614 set [ADR-137](../../record/decisions.d/ADR-137.md) Active and [RETRO-008](../../record/retrospectives.d/RETRO-008.md) Accepted. When docs-generate finished, the back-merge of main into staging found the same two files changed on both sides and stopped: "main does not merge cleanly into staging; resolve by hand".

**How it was found.** The Docs workflow on main failed in its back-merge job. The assistant was waiting for the back-merge before filing the next batch, and saw the failure when it checked.

**The fix.** A branch cut from staging, with `origin/main` merged into it. Each conflict was resolved by keeping main's concretized file (its number, `formerly:` and permanent codes) and reapplying 614's edits by script: status, version 2 and history, `prompted`, and the responses section. The branch then went to staging as a pull request. The old spellings left in 614's own new files are upgraded by `luria repair` in the pull request's docs-check, so they were not rewritten by hand.

**What to keep.** Between a merge into main and its back-merge, staging should take no merges that edit entries in the batch being promoted. The promotion is concretizing those very files. The next merge into staging waits for the back-merge commit, or for the back-merge job's failure, as here.
