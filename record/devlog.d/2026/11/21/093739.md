**What happened.** After the owner merged the promotion pull request (582) into main, its codes were made permanent, and four open pull requests still cited the old temporary codes. The assistant merged staging into each and ran a script that replaced every temporary code with its permanent one, using each entry's `formerly:` field as the map. The script also replaced the codes inside `formerly:` itself, so [CLAIM-181](../../record/claims.d/CLAIM-181.md)'s history read `formerly: CLAIM-181`. That happened in 24 entries on one branch and a few on others. Three of the branches were pushed before the assistant noticed that the rewrite had touched many more files than it expected.

**How it was found.** Before pushing the fourth branch, the assistant read one rewritten file instead of trusting the count.

**The fix.** `git revert` of the three pushed commits, and a rewrite that skips the `formerly:` list. A check over every file each branch changes then found no stale temporary code left. No branch's history was rewritten, and nothing reached staging.

**What to keep.** A mechanical rewrite of codes should leave alone any field that records codes as history (`formerly:`). Read one changed file before pushing a script's output, whenever the number of files changed is larger than expected. Luria's own `concretize` and `unconcretize` know this; a hand-rolled rewrite does not.
