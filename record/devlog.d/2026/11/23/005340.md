created: '2026-11-23T00:53:40'

---

**Going wrong, found by the owner.** The owner noticed that temporary codes
had gone from `formerly:` lists. They had not been deleted: each list held
the entry's own concrete code in their place, so CLAIM-626 listed itself
as formerly CLAIM-626.

The cause was a back-merge of staging into a lead's branch after a
promotion (commit b23754a0, merged with pull request 746). Its message
says the conflict hunks kept the branch's side "with every temporary code
that a staging entry lists under formerly: written as that entry's
code". That rewrite was meant for citations. Applied to every
occurrence, it also hit the `formerly:` field, where the temporary code
is the point. Both parents of that merge held the right list, and the
merge result did not. That cost 28 entries on staging.

**The wrong theory, and how it fell.** The first search looked for
removed `formerly` lines and found only link repairs. A comparison of
`formerly` lists between main and staging found the 28. The first guess
was a conflict resolved to the branch's stale copy. Reading the two
parents showed both had the list right, so the merge had rewritten it.
A scan for any entry whose `formerly` contains its own code then found
28 more, already on main from earlier merges, which predate this
session's clone depth. A deeper fetch of main's history recovered them
from each entry's first concretized version.

**The fix.** All 56 were restored. A check now passes: no entry lists
itself, every front matter parses, and no temporary code is claimed by
two entries. The run-lead skill states the rule. A lint check (an entry's
`formerly` must not contain its own code) would make it a mechanism
(DP-3). That is a CI change and is left for the owner.
